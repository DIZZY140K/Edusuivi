Description dynamique : Saisie des notes

Ce diagramme montre la séquence d'événements lancée lorsqu'un enseignant accède à sa grille de saisie en masse pour sa classe assignée. Il illustre le processus de vérification d'existence préalable (requête SQL conditionnelle) afin de décider s'il faut exécuter un UPDATE ou un INSERT.

sequenceDiagram
    actor Teacher as Enseignant
    participant Browser as Navigateur Client
    participant Server as Serveur PHP (teacher/grades.php)
    participant DB as Base de Données (MySQL)
    
    Teacher->>Browser: Sélectionne Classe, Matière et Période
    Browser->>Server: HTTP GET /teacher/grades.php?class_id=X&subject_id=Y
    Server->>DB: Récupère la liste des élèves de la classe
    DB-->>Server: Données élèves (ID, nom, matricule)
    Server->>DB: Récupère les notes existantes si saisies
    DB-->>Server: Liste des notes
    Server-->>Browser: Affiche la grille de saisie en masse
    
    Teacher->>Browser: Remplit les notes et commentaires
    Teacher->>Browser: Clique sur "Enregistrer toutes les notes"
    
    Browser->>Server: HTTP POST /teacher/grades.php (grades[student_id], comments...)
    Note over Server: requireRole('teacher') & validation des données
    
    loop Pour chaque élève
        Server->>DB: SELECT id FROM grades WHERE student_id=? AND subject_id=? AND period=?
        DB-->>Server: Retourne l'id (s'il existe)
        
        alt La note existe déjà
            Server->>DB: UPDATE grades SET grade=?, comment=? WHERE id=?
        else Nouvelle note
            Server->>DB: INSERT INTO grades (student_id, subject_id, teacher_id, grade, comment...)
        end
        DB-->>Server: Confirmation SQL
    end
    
    Server-->>Browser: HTTP 200 OK (Redirection + Message de succès)
    Browser-->>Teacher: Affiche "X note(s) enregistrée(s) avec succès."

Description dynamique : Enregistrement Paiement

Ce diagramme détaille la cinématique d'un encaissement de frais scolaires par l'administrateur. Il montre l'importance de la génération du numéro de reçu unique (REC-YYYY-XXXXX) et l'insertion en cascade d'une alerte/notification destinée au parent associé.

sequenceDiagram
    actor Admin as Administrateur
    participant Browser as Navigateur (Admin)
    participant Server as Serveur PHP (admin/fees.php)
    participant DB as Base de Données (MySQL)
    actor Parent as Parent (Notification)
    
    Admin->>Browser: Sélectionne l'élève & Clique sur "Enregistrer paiement"
    Browser-->>Admin: Ouvre le modal de paiement
    Admin->>Browser: Remplit le type de frais, montant, mode (Cash/M-Pesa...)
    Admin->>Browser: Soumet le formulaire
    
    Browser->>Server: HTTP POST /admin/fees.php (action=pay, student_fee_id, amount_paid...)
    Note over Server: requireRole('admin') & Validation du montant
    
    Server->>DB: INSERT INTO fee_payments (student_fee_id, student_id, amount_paid, payment_method, recorder_by...)
    DB-->>Server: Confirmation (Paiement inséré)
    
    Server->>DB: SELECT parent_id FROM students WHERE id = student_id
    DB-->>Server: ID Parent (ex: 3)
    
    alt Le parent est associé
        Server->>DB: INSERT INTO notifications (user_id, type, title, body, link)
        DB-->>Server: Confirmation
    end
    
    Server-->>Browser: HTTP 200 OK + Message ("Paiement enregistré")
    Browser-->>Admin: Affiche le reçu de paiement généré
    
    Parent->>Browser: Se connecte ou actualise sa page (parent/index.php)
    Browser->>Server: HTTP GET /api/notifications.php
    Server->>DB: SELECT * FROM notifications WHERE user_id=? AND is_read=0
    DB-->>Server: Liste des notifications (incluant le paiement)
    Server-->>Browser: Réponse JSON / HTML
    Browser-->>Parent: Affiche une alerte/badge rouge + Détail: "Paiement enregistré: Reçu REC-..."

Description physique

Ce diagramme illustre le déploiement physique de l'architecture 3-tiers de l'application dans son environnement cible (XAMPP). Il sépare le poste client (navigateur), le serveur web (Apache), le serveur d'application (PHP 8 + PDO) et le serveur de données MySQL.

flowchart TB
    subgraph ClientDevice ["Poste Client (Ordinateur / Mobile du Parent ou Enseignant)"]
        Browser ["Navigateur Web (Chrome, Firefox, Safari)"]
        UI_Runtime ["Runtime Client (HTML5 / CSS3 / Vanilla JS)"]
        Browser --- UI_Runtime
    end

    subgraph ServerNode ["Serveur Physique / Virtuel (ex: Machine Locale avec XAMPP sous Windows OS)"]
        subgraph WebServer ["Serveur Web (Apache HTTP Server 2.4+)"]
            Apache ["Processus Apache"]
            HTTP_Config ["Fichiers .htaccess / Configuration ports (80/443)"]
            Apache --- HTTP_Config
        end
        
        subgraph AppRuntime ["Moteur d'Application (PHP 8.x)"]
            PHP_Engine ["Moteur PHP 8"]
            PDO_Extension ["Extension PDO MySQL"]
            AppCode ["Fichiers sources php (index.php, admin/, teacher/, parent/)"]
            PHP_Engine --- PDO_Extension
            PHP_Engine --- AppCode
        end

        subgraph DBServer ["Serveur de Base de Données (MySQL / MariaDB)"]
            MySQL_Engine ["Moteur de Base de Données (Port 3306)"]
            Database ["Schéma edusuivi (Tables, Index, Contraintes de clés)"]
            MySQL_Engine --- Database
        end
    end

    Browser -- "HTTP / HTTPS (Port 80/443)" --> Apache
    Apache -- "Interprète / Exécute scripts" --> PHP_Engine
    PDO_Extension -- "Connexion Socket TCP/IP (Port 3306)" --> MySQL_Engine

Description comportementale : Diagramme d'Activités

Ce diagramme d'activités modélise les flux de travail principaux de l'application EduSuivi selon les trois rôles : Administrateur (gestion des élèves, classes, frais, statistiques), Enseignant (saisie des notes en masse, signalement des absences) et Parent (consultation des notes, absences, frais et bulletins). Les actions communes (messagerie, notifications, profil) sont partagées entre tous les acteurs. Chaque décision métier clé est représentée par un losange de condition.
